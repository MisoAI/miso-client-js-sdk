# Client SDK Workflow

The workflow package (`std:workflow` plugin) hosts the client-agnostic workflow layer of the Miso SDK: workflow classes, actors, and the default-options store. It has no DOM dependency at import time, so it can be loaded and tested in Node. The presentation layer (custom elements, layouts) lives in `client-sdk-ui`, which builds on this package.

## Architecture Overview

The central concept is a **hub-and-spoke model per workflow instance**. Each `Workflow` owns a private `Hub` (a pub/sub state store) and a set of **actors** that only communicate through hub fields — actors never call each other directly. The UI package's custom elements and layouts plug into a workflow's views actor.

```
WorkflowPlugin ('std:workflow', singleton)
 ├─ WorkflowDefaults store (default options per workflow name)
 │    ├─ seeded with non-layout options (api, trackers, pagination, autocomplete, filters)
 │    │  by the plugin itself (default-options.js)
 │    └─ seeded with layout options + UI templates by the UI plugin (std:ui)
 ├─ injects client.workflows on each MisoClient instance (workflows.js):
 │    search, hybridSearch, asks/ask, explores/explore, recommendations/recommendation,
 │    history, conversation, messageItems, threadItems; plus events — the per-client event bus (an EventEmitter shared by
 │    all workflow instances of the client; no built-in workflow uses it since
 │    History/Conversation switched to direct calls)
 ├─ layouts registry reference, provided by the UI plugin via setLayouts()
 └─ exposed via the `workflows` plugin extension point

Workflow instance (e.g. one Ask)
 │ owns
 ▼
┌────────────────────────── Hub (private to this workflow) ──────────────────────────┐
│  fields: session, query, request, response, data, view:<role>, tracker,            │
│          interaction, input, completions, filters, feedback, more                  │
└─────────────────────────────────────────────────────────────────────────────────────┘
   ▲              ▲               ▲                    ▲                  ▲
SessionMaker   DataActor      ViewsActor          TrackersActor    InteractionsActor
(session)      (request →     (data → render      (visibility →    (interaction →
                response)      via ViewActors)     tracker)         send to API)
                                   │
                                   │ one ViewActor per element = (element, layout, role)
                                   ▼
                     <miso-*> elements + layout instances (client-sdk-ui)
```

Key points that are easy to get wrong:

- The Hub is **per workflow instance**, not global. Two `<miso-ask>` follow-up sections have two hubs.
- Workflows read their default options from the plugin's defaults store at creation (`base.js` → `plugin.defaults.get(name)`; the plugin arrives through the constructor, directly or via the context — never through a module-level singleton, which would create a cyclic import). Keyed by workflow name (`ask`, `search`, `hybrid-search`, `recommendation`, `explore`); defaults must be set before the workflow instance is created. Two workflows (`autocomplete`, `hybrid-search/answer`) receive `defaults` explicitly instead.
- The workflow object itself is the coordinator and public API surface (`query()`, `start()`, `restart()`, `useApi()`, `useLayouts()`, ...). It reads/writes hub fields like the actors do, and derives its lifecycle events from the main role's `view:<role>` state.

## Core Directories

| Directory | Purpose |
|-----------|---------|

| `src/actor/` | The `Hub` itself, hub field names (`fields.js`), and the actors: `SessionMaker`, `DataActor`, `ViewsActor`/`ViewActor`, `TrackersActor`, `InteractionsActor`, `FeedbackActor`; plus `ThreadsModel`, the per-client model of thread operations shared by the history/conversation peers |

| `src/default-options.js` | Built-in non-layout default options per workflow, seeded into the store by the plugin |
| `src/defaults.js` | `WorkflowDefaults` — the defaults store |
| `src/source.js` | Adapts `client.api.*` into the data source function `DataActor` calls |

## Workflow class hierarchy

```
Workflow (base.js: hub, actors, session, data pipeline, interactions)
├── AnswerBasedWorkflow (query flow, answer/citation handling, feedback)
│   ├── Ask
│   ├── HybridSearchAnswer (internal to HybridSearch)
│   └── MessageItem (one conversation message, behind <miso-message-item>; data actor off — fed by Conversation via updateData())
├── SearchBasedWorkflow (products/results, pagination, facets)
│   ├── Search
│   └── HybridSearch
├── UnitWorkflow (bound to a unit id, started via start())
│   ├── Explore
│   └── Recommendation
├── History (thread list of the chat history interface, user history API)
├── Conversation (conversation panel showing one thread at a time; History's independent peer — thread mutations go through the shared ThreadsModel)
├── ThreadItem (one thread list item, behind <miso-thread-item>; data actor off — fed by History via updateData())
└── Autocomplete (attached to query inputs)

WorkflowContext (context.js)
├── Asks — multiple Ask instances forming a follow-up chain
├── MessageItems — MessageItem instances keyed by question id (the conversation panel's items)
├── ThreadItems — ThreadItem instances keyed by thread id (the thread list's items; holds the shared ThreadsModel for their mutations)
└── UnitWorkflowContext — Explores, Recommendations (instances keyed by unit id)
```

Multi-instance management is a first-class concept, surfaced at `client.workflows` (the `client.ui.*` equivalents delegate here for backward compatibility):

- **Asks**: `client.workflows.asks.root` is the initial question; each follow-up is a *separate* `Ask` workflow keyed by `parentQuestionId` (`getByParentQuestionId(id, { autoCreate })`). Workflows chain via `previous`/`next`, and `asks.active` tracks the currently loading one.
- **Explores/Recommendations**: instances keyed by unit id (`client.workflows.recommendations.get(unitId)`, default unit id `'default'`).
- **Search/HybridSearch**: single lazily-created instances per client (`client.workflows.search`).
- **History/Conversation**: the chat-history interface (thread list + conversation panel). Both are lazily-created singletons per client — **peers, created independently** by their own accessors (`client.workflows.history` / `.conversation`): each looks the other up from the workflows registry **without constructing it** (the `_peer` getter reads the raw cache field), and every cross-call is guarded by the peer's presence, so either panel works standalone. Thread **mutations** — and the thread-detail read (`getThread`) — go through the shared **`ThreadsModel`** (`actor/threads.js`, one per client, created by `Workflows` and handed to both constructors): a model mutation (`rename`, `markAsRead`, `subscribe`/`unsubscribe` — answer-updates subscription; `subscribed` and `has_new` are independent facts, and the unread presentation (`isThreadUnread`, the UI red dot) derives from `subscribed && has_new` — `delete` — one id or an array — `deleteAll`) calls the API, then **emits the fact** (`updated`, `deleted`, `all-deleted`), which each constructed workflow subscribes to and applies to its own data downstream (`_onThreadUpdated` / `_onThreadDeleted` / `_onAllThreadsDeleted`, implemented per side) — so a change goes through the same code path whichever side it originated from; History exposes the mutations id-based (`rename(threadId, title)`, ...), Conversation against the thread on display (see below). The two coordinate by **direct method calls** (the event bus, `client.workflows.bus`, is not involved): History's `select()` loads the selection into the conversation panel (`_onThreadSelect`); Conversation marks a loaded thread as read (`_markThreadAsRead`) — right at load() time, so the unread dot clears immediately (skipped when no history workflow is around: no unread state is tracked); the panel's displayed record simply never carries the unread flag — an open thread is read by definition (`writeThreadAsRead` in `workflow/processors.js` stamps `has_new: false` whatever the response says). Conversation's member roles cover the panel's own widgets: `messages`, `query`, plus the header roles `title`, `rename`, `delete` and `subscription`, whose mappings are **dot-path strings** into the open thread's record (`'thread.title'`, `'thread'`, `'thread'`, `'thread.subscribed'` — `asMappingFunction` resolves dot-separated paths against the data value; rename and delete take the whole record so their button layouts can derive the dialog text and the disabled state — they disable while the record has no thread id, i.e. until a thread being created resolves); the rename button pre-fills its dialog with its mapped title and its `submit` event carries the confirmed text into `rename(value)`; the delete button's confirm dialog interpolates its mapped title, its confirmed `submit` (`_onViewDeleteSubmit`) routing to `delete()` — the deletion fact then resets the panel to new-thread mode — and the subscription checkbox renders its checked state from data, its `change` view event (`_onViewSubscriptionChange`) routing to subscribe()/unsubscribe(); none is a *data* role, so they do not affect the container's empty/nonempty status. Conversation also exposes the thread operations on the thread on display — `rename(title)`, `subscribe()`, `unsubscribe()`, `delete()`, the shared mutations resolved against the loaded thread (a thread being created has no server identity to operate on). Thread-record shape logic — normalization, merging, and the semantic predicates — is centralized in `src/util/threads.js` because the history API shape is still a prototype; simple field reads (`thread_id`, `placeholder_id`, `question_id`, ...) are inlined at the call sites, and the response-shape fallbacks live at the API boundary instead (`processResponse()` in `source.js` fills a thread record's canonical fields from their alternatives: `question_id` -> `thread_id`, `time` -> `updated_at`), so the workflows read canonical fields only. **A thread's id is the id of its first question** — a contract the new-thread flow relies on. The workflows are written against the resource-style user history API (`client-sdk-core`'s `api/history.js`, not released yet); the **deployed v0 API** (flat, POST-only, threads addressed by root question id) is adapted behind that same interface by `api/history.0.js` in the core package — currently the one in use — so nothing here is version-aware. The thread detail is **assumed to return the same thread properties as the thread list API**, so the panel reads the thread record off the head response alone: the history selection hands over only the thread id (`select()` -> `_onThreadSelect(threadId)` -> `load(threadId)`), with no list record passed along — History skips the delegation entirely for a placeholder item, whose id must never address the API. (The doggoganger mock's v0 `openThread` does not return these properties yet; one lorem test carries a TODO until it does.) Conversation's processing splits along the pipeline deliberately: `_defaultProcessData` **homogenizes** every request type's value to the canonical `{ thread, messages }` shape but merges nothing, while merging into the current data happens in `_updateDataInHub` — past the custom `dataProcessor` passes — so each piece of data runs through the custom processors exactly once, in one shape. Conversation's **sole api option is the answers api**; its data flow takes **two requests per session**, both going down the standard data path via `_request()` (the search-based query/more pattern, split by `request.type` — `REQUEST_TYPE.THREAD` head / `REQUEST_TYPE.ANSWERS` follow-up): the head request (`GET threads/{id}`) yields turns as question ids — **fetched through the ThreadsModel in place of the data actor**: the request carries `actor: false` (a per-request switch the DataActor honors) with its identity spelled out at the call site (`load()`), and Conversation's own `request`-field wiring (`_onRequest`) calls `model.getThread()` and feeds the hub `response` field, so the request/response events flow as usual; the follow-up (`ask.answers`) is **a polling iterable owned by the api layer**, like an ask answer stream: `client.api.ask.answers()` returns an `Answers` iterable stub (core `api/ask.js`), and the request's payload gives **`question_ids` as a function**, resolved by the stub for every poll — **the pending question ids read off the current data** (`getUnsettledQuestionIds`: any non-live message whose answer is absent or `finished: false`), so settled messages drop out between polls, new ones (e.g. further pages, later) are picked up, and one request suffices while a poll runs (the DataActor's `polling` state — whether a request is being served — gates re-requesting; a later unsettled batch starts a new stream) — until nothing is left, ending the stream (a fixed initial id array is mutable all the same: its ids settle out as their records come back finished). The stub's polling drops a late, outdated response by its fetch-issue index, and the data actor consumes the iterable like any streamed response — abort on new session included (`api.options.pollingInterval`, default 1s; the stub fires its first fetch immediately) — so an answer still generating is picked up even after switching away and back to the thread; its response is merged into the head data's messages in `_updateDataInHub` (`mergeAnswersDataFromResponse`, the `concatItemsFromMoreResponse` analogue) — its loading update keeps the head data on display, and the head request is restored on the merged data, so the follow-up stays an internal detail. Conversation also posts **questions** (`send(question)`, fed by the search box's `submit` view event — its own `_onQuerySubmit`: the panel has no query flow), but **the live message delivers itself**: send() appends the optimistic record (`live: true`, keyed by a local `placeholder_id` until the response brings the question id), and the message's own item subworkflow posts the question and streams the answer, ask-style (`MessageItem.post()`: the query flow through its data actor, `ask.questions` + `parent_question_id`, payload carrying `question_source: _organic`), while Conversation **follows the stream** (`_followLiveMessage`, subscribed to the message workflow's data field), folding each streamed value back into its own record (`_patchLiveMessage`, keyed by the placeholder id) — the fold simply misses once the panel has moved on to another session. History's new-chat action (wired to the standalone new-thread component (`<miso-new-thread>`), `ROLE.NEW_THREAD`, via its `submit` view event) clears the selection and calls the conversation's `new()`, which enters new-thread mode — a no-op (no new session, no re-render) when the panel already sits on an untouched new thread, i.e. it holds neither a thread id nor a placeholder id; pass `{ force: true }` to `new()` to reset regardless. Conversation starts (and resets) in **new-thread mode**: a local placeholder thread with no messages, committed as ready data. `send(question)` posts to the current thread, or, with no thread loaded, starts a new one: it announces the placeholder to History (`_onConversationNew`: appends and selects a placeholder item), posts the question as a root ask (through the live message workflow), and — once the stream carries the question id — settles the placeholder **immediately** (`_resolvePlaceholder`, on the first streamed chunk): that question id **is** the thread id, and the resolution involves **no server round trip at all** — no reload, no thread-detail fetch. It is announced to History (`_onConversationResolve(placeholderId, threadId)` — the thread id being the only thing the resolution gains), which settles its own listed placeholder item around it, and the panel settles its own displayed record likewise (`settlePlaceholder`, shared in `util/threads.js`) — with the placeholder gone from both records, the resolution structurally cannot fire twice, so no dedup flag is needed. The local fields (title, updated_at) stand in until the next thread list load; the posted answer just keeps streaming into the panel. Leaving the panel mid-creation (selecting another thread, or new chat) is safe: **the live message workflow outlives the panel's session**, so when its stream brings the question id — the thread id, by contract — the resolution (`_resolvePlaceholder`) still lands: the listed side settles its placeholder item, while the panel's own record settles only if the thread is still on display (there is no expired-response scavenging anymore — the stream never expires with the panel's session). Either way the placeholder item stays in the list and settles in place into a selectable record — never removed, no list reload. A thread being created has **no thread id at all**: its placeholder record is keyed by a local `placeholder_id`, so nothing can address it as a thread server-side. Neither workflow keeps state fields of its own — everything lives in the data layer: Conversation's `threadId` is the committed thread record's id, falling back to the in-flight head request (which carries `threadId` explicitly), the creating state is recognized by the committed placeholder record, and History's selection (`selectedId`) is the `selectedThreadId` of its committed value — mutations patch it together with the threads in one commit, `_defaultProcessData` carries it over onto fresh server responses (which bring none of their own), so it survives a refresh, and the same pass stamps each record's `selected` flag, so the thread items carry their selection state in the data layer — the thread-id-presence checks in the view action handlers (select, delete) are what keeps a placeholder item from reaching the API. Item identity for selection and lookup is the thread id, falling back to the placeholder id (inlined as `thread.thread_id || thread.placeholder_id`; there is deliberately no combined helper). Conversation itself sends no answer-content interactions: rendering, trackings, and feedback of the panel's items all live on the **message item subworkflows** (next bullet); posted question payloads carry `question_source: _organic` like ask's (`writeQuestionSourceToPayload` in `send()`).
- **Messages**: the conversation panel's items as workflows of their own — one `MessageItem` per message, managed by the `MessageItems` context (`client.workflows.messageItems`), in the manner of the ask chain. The messages layout is a **shell**: it renders one `<miso-message-item>` container element per item and **binds it implicitly** off the item binding (`element.workflow = conversation.getMessageWorkflow(record)` in the post-render sync pass); role elements inside bind to the message workflow as usual (`getContainer` resolves to the closest container ancestor). A hand-placed `<miso-message-item question-id="...">` binds explicitly through its parent container's workflow instead. Identity: keyed by **question id, falling back to the local `placeholder_id`** the optimistic record gets stamped in `send()` — so a **just-posted message has a workflow before its question id exists**, and adopts the id when the response arrives (`MessageItem._writeQuestionId` registers it at the context; `_clearQuestionId` is a no-op — a restart never drops the identity): one workflow, one continuous session across the settle. The **parent question id is part of the identity too** — a message's lineage never changes — passed into the constructor off the record (`send()` stamps `parent_question_id` on the optimistic record, from the last message at posting time, so live and server records carry the lineage alike) and written into the posted payload from there (`_buildPayload` reads `this.parentQuestionId`, like Ask). `MessageItem` is **answer-based, delivering its own data only when live**: a live message posts its question and streams the answer through its own data actor, ask-style (`post()` sends the optimistic record along the query flow and `_query` puts it **on the request**; the default data pass merges it under every committed value — `writePostedMessageToData`, the `writeKeywordsToData` pattern: everything derives from the data itself, no state field on the workflow — because the streamed values carry the answer content only: the record supplies the question and identity fields (`question`, `placeholder_id`, `live`) throughout, so the question shows from the request's loading commit on, with no separate seed commit; its api option is the ask questions endpoint — configurable via `client.workflows.messageItems.useApi(...)` — with `source_fl` extended with `title`/`authors` for the compact source cards); a message that is **not** live has its actor turned off per instance (`useApi(false)`, applied by the MessageItems context at creation) and the conversation **propagates its record in through `updateData()`** on every data commit (`_updateMessageWorkflows`, resolving instances via `context.get(record)`, skipping live records — only ever existing instances: workflows are created by elements or by send(), never by data, so nothing is constructed when `<miso-message-item>` is not in play; an identity check skips records already on display). `_shallHandleAsHeadResponse` returns false so committed records go straight down the pipeline; a record without its answer body presents as status `loading` — the standard container status mark; there is deliberately no per-message loading icon — and an unfinished record — `finished: false` — keeps the data `ongoing`. Each message workflow holds its **own roles, layout options** (`'message-item'` in the UI defaults: the answer-based layouts minus the query role, `logo: false`, the `question` layout for the question role — text plus authorship attributes, off the whole record via the role mapping — the hybrid-search-style compact horizontal cards for the sources (the conversation's `query` api payload extends `source_fl` with `title`/`authors` for them — the payload options are effective on the query api only, the messages endpoint ignores them), and the answer typewriter with `instant: true` — an answer that finishes before any of it was typed renders in one shot, only content streaming in as it is generated types out; the caret blinks while loading, the standard typewriter loading indication) **and trackers**, so answer-content interactions — citation clicks, answer link clicks, feedback — run through the standard answer-based machinery and **deduplicate at the message level**; each interaction carries the message's question lineage (`_writeMessageInfoToInteraction`: `parent_question_id` and `miso_id` off the record — **the question chain may fork**, so the parent is never inferred from message order — `root_question_id` = the conversation's thread id, `question_source` `_update`/`_organic` via `isUpdateMessage`; `question_id` comes from the record via the answer-based pass). Inline follow-up links submit through the conversation's `send()` (`_onFollowUpClick` delegates to the conversation workflow, if constructed).
- **Threads**: the thread list's items as workflows of their own — one `ThreadItem` per listed thread, managed by the `ThreadItems` context (`client.workflows.threadItems`), in the manner of the conversation's message items. The threads layout is a **shell**: it renders one `<miso-thread-item>` container element per item and binds it implicitly off the item binding (`element.workflow = history.getThreadWorkflow(record)` in the post-render sync pass); role elements inside (`title`, and the context menu's `rename`/`delete` buttons, plus `subscription` for custom item bodies) bind to the thread workflow and render through the generic text/button/checkbox layouts — title and subscription map dot-paths into the record (`'title'`, `'subscribed'`), rename and delete the whole record (their button layouts derive the dialog text from its title and disable while it has no thread id yet). A hand-placed `<miso-thread-item thread-id="...">` binds explicitly through its parent container's workflow instead. Identity: keyed by **thread id, falling back to the local `placeholder_id`** of a thread being created; the settled record no longer carries the placeholder id, so the adoption happens at the resolution (`History._onConversationResolve` → `ThreadItems._resolvePlaceholder` → `ThreadItem._writeThreadId`, before the records are patched) — one workflow, one continuous element binding across the settle. A `ThreadItem` **never delivers data of its own**: its data actor is off (`useApi(false)`, applied by the context at creation) and History propagates records in through `updateData()` on every data commit (`_updateThreadWorkflows`, only ever into existing instances — workflows are created by elements, never by data — with an identity check skipping records already on display). **Record identity is the change signal**: History's stamp-only passes preserve the identity of untouched records (`_defaultProcessData` re-stamps `selected` only where the flag flips), so a rename, selection change, or subscription toggle re-renders the affected items' roles alone — nothing else commits. View events route to the shared `ThreadsModel` directly (`rename` submit, `delete` submit, `subscription` change), guarded by the thread id's presence so a placeholder never addresses the API; the facts come back through History's model subscriptions and flow down the propagation path. Item selection stays list-level: the shell emits the `select` view event on History's `threads` role, as before; the item's context menu markup comes from the item template, its open/close behavior driven by the thread workflow's container role (the UI's `item-container` layout, by the `item-menu` data-role contract). Created with `superworkflow: history`, so any interactions report `workflow: 'history'`.

Workflows are configured via `use*()` methods (`useApi`, `useLayouts`, `useDataProcessor`, ...) from `workflow/options/`; options cascade defaults store → context → workflow. Every workflow is built around a **single api endpoint option** (`useApi()`, feature key `api`): the conversation's is the answers api — its head (thread) request is served by the ThreadsModel with the request identity spelled out at the call site, and the question posting belongs to the live message workflow, configurable via `client.workflows.messageItems.useApi(...)` (the context cascade), keeping the ask/hybrid-search experience. Api call `options` (such as `pollingInterval`) are configured through the defaults store.

## Default options

`WorkflowDefaults.set(name, options)` merges shallowly per feature key. Precedence at resolution: store defaults < context options < workflow-local `use*()` options.

- The **workflow plugin** seeds everything except layouts (`default-options.js`).
- The **UI plugin** seeds `layouts` (and the ask `templates.followUp`) at its install.
- Integrators may override via the `workflows` extension point or `MisoClient.plugins.get('std:workflow').defaults.set(...)` — before workflows are created.

## Hub & Actors

`Hub` is a minimal pub/sub store: `update(field, state)` (persist + emit) and `trigger(field, payload)` (emit only). All coordination goes through these fields (see `actor/fields.js`):

- `session` — current session (uuid); stale-session data is discarded everywhere
- `query` — user query submission (from search box layout or `workflow.query()`)
- `request` — resolved API request (workflow merges api options + session)
- `response` — raw API response(s); streamed responses emit repeatedly; a response arriving after its session expired never enters the data flow, but is announced on the trigger-only `expired-response` field for the workflow to salvage what it can
- `data` — processed response (status, revision-guarded) that views consume
- `view:<role>` — per-role view state (status, ongoing, session, meta)
- `tracker` / `interaction` — tracking events and outgoing interaction payloads

Actors, each subscribing to some fields and updating others:

- `SessionMaker` — creates sessions on `restart()`
- `DataActor` — `request` → calls the API source → `response`; handles async-iterable (streaming/polling) responses, abort-on-new-session, and per-request bypass (`actor: false` on the merged request)
- `ViewsActor` — `data` → refreshes its `ViewActor`s; manages element/layout pairs, per-role data slicing (role mappings), and empty-state detection
- `TrackersActor` — observes rendered items (impression/viewable/click) → `tracker`
- `InteractionsActor` — `interaction` → sends to Miso API via the client

## Roles & Status

**Roles** (`constants.js` `ROLE`): identify what data slice a view displays. Each workflow declares its member roles, a `main` role (answer for ask, products for search), and per-role data mappings (`ROLES_OPTIONS` in each workflow file).

**Status** (view state): `initial` → `loading` → `ready` | `erroneous`, with `ongoing: true` while a streamed answer is still updating. Workflow lifecycle **events** (emitted once per session, derived from the main role's view state): `loading`, `ready`, `done`, `error`, `interrupt` (superseded by a new question), `finally`.

## Data Flow (one query, end to end)

1. Query enters: user submits in the search box layout, which emits a `submit` **view event** on the query role — each query-hosting workflow subscribes and routes it itself (`_onQuerySubmit` → `query({ q })` in the answer-based, search-based and explore workflows; Conversation routes to `send()` — nothing in the base class) — or code calls `workflow.query({ q })`; unit workflows (explore, recommendation) start via `start()` instead. `query()` starts the new session (restart) **before** updating hub field `query` — the hub queues reentrant emissions, so a restart inside the dispatched `_query()` handler would land its session-reset data commit after the request's loading commit. Layouts emit view events; they never write the query field or call workflow methods directly.
2. Workflow merges API options with the request and updates hub field `request` (tagged with the current session).
3. `DataActor` picks up `request`, calls the API through `source.js`; for streaming answers it iterates the async response and updates `response` repeatedly. Responses for stale sessions are dropped.
4. Workflow picks up `response`, runs the data pipeline (status/meta stamping, revision check, custom `dataProcessor` passes) and updates `data`.
5. `ViewsActor` picks up `data` and refreshes every view: each `ViewActor` slices data by its role mapping and calls `layout.render(element, data, { notifyUpdate })`.
6. Layouts call `notifyUpdate()` → view state published to `view:<role>`; the workflow watches the main role's view state to emit lifecycle events (`loading`, `ready`, `done`, ...).
7. `TrackersActor` observes rendered items for impression/viewable/click and triggers `tracker`; the workflow builds the interaction payload (session, request, miso_id, custom context) and triggers `interaction`; `InteractionsActor` sends it to the API.
8. `restart()` starts a new session: in-flight fetches are aborted, stale hub data is ignored, and (for Ask) downstream follow-up workflows are destroyed.
